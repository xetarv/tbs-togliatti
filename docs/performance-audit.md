# Аудит производительности игры

Дата измерений: 8 октября 2026, UTC; работа продолжалась 9 октября по Europe/Samara.

**Статус: диагностика, без оптимизации и без изменения игровой логики.** Пользователь потребовал согласовать план перед исправлениями. Затем попросил завершить текущую проверку памяти, сохранить результаты и не начинать новых исследований из-за оставшегося лимита. В продолжении были разрешены адресные проверки census, затем пользователь снова остановил новые тесты для переноса работы на другой компьютер. Ниже сохранены успевшие завершиться результаты.

## Вывод

Просадка воспроизведена на аппаратном WebGL с RTX 2080 Ti: в тяжёлых сценах около **34–43 FPS при 1920×1080 и высоком качестве**. На основной цикл кадра приходится 22,8–28,7 мс; из них 21,9–27,8 мс занимает вызов графического конвейера. Физика, логика трафика и камера существенно дешевле. Главный поток практически постоянно занят; GPU также превышает бюджет 16,67 мс в ночной сцене. Это подтверждённая проблема рендеринга, а не основание заново переделывать архитектуру.

**Результатов «после оптимизации» нет: исправления не проводились.** Ускорение нельзя считать доказанным до сопоставимых повторных измерений.

## Условия и методика

- CPU: Intel Core i7-9700K, 8 логических процессоров; RAM около 32 GiB.
- Windows 10, build 19042; Chrome 154.0.8037.99; Three.js r149 из локального `assets/three.min.js`.
- Активный WebGL: ANGLE / NVIDIA GeForce RTX 2080 Ti / Direct3D 11. Также установлена GTX 1080 Ti; измерения относятся к выбранной Chrome RTX 2080 Ti.
- Playwright запускает отдельный Chrome headless с аппаратным ускорением: `--enable-webgl --use-angle=d3d11 --enable-precise-memory-info`. SwiftShader не использовался. Viewport и drawing buffer 1920×1080, DPR 1, preset `high`. Искусственного CPU throttling нет. Звук включается обычным нажатием «Начать».
- FPS рассчитан как 1000 / средний фактический интервал между вызовами игрового шага. Это частота обработки кадров в браузере headless, **не прямое измерение вывода на физический монитор**. Вертикальная синхронизация и задержка ввода на мониторе отдельно не проверялись.
- CPU-время кадра — wall time `game.step`; время рендера — wall time `graphics.render`. Они включают возможное ожидание драйвера и не равны исключительно вычислениям CPU.
- GPU-время измерено асинхронно через `EXT_disjoint_timer_query_webgl2`, примерно каждый четвёртый кадр; disjoint-результаты отбрасываются. CPU и GPU работают с перекрытием: складывать эти времена нельзя.
- Draw calls и треугольники взяты из `renderer.info`: сброс один раз на игровой кадр, учитываются основной проход, тени, отражения и постобработка. Это количество отправленной геометрии, а не число видимых на экране треугольников.
- Занятость главного потока рассчитана из CDP `Performance.getMetrics`, `TaskDuration / Timestamp`; это доля времени в задачах, **не процент загрузки всех ядер компьютера**.
- Перед окнами измерений выполнялся прогрев. Основные неподвижные сценарии повторены трижды по 20 секунд. В таблице ниже объединены интервалы всех трёх повторов; p95/p99 — соответствующие перцентили времени кадра.
- CPU sampling и Chrome trace записывались отдельно от основных FPS-окон. Их накладные расходы не смешаны с основной таблицей.
- Инструментирование подключалось только в диагностическом экземпляре браузера через init-script. Файлы игры не редактировались. Сопоставление минимального и полного инструментирования: 54,76 и 54,55 FPS; разница 0,37%, при немного разном положении NPC и числе draw calls. Это оценка небольших накладных расходов, а не доказательство их полного отсутствия.

Методические источники: [Chrome Performance](https://developer.chrome.com/docs/devtools/performance/reference), [Chrome: диагностика памяти](https://developer.chrome.com/docs/devtools/memory-problems), [Khronos: GPU timer queries](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/).

## Подтверждённые проблемы и их приоритет

### 1. Большая стоимость подготовки и отправки сцены — основной приоритет для устойчивого FPS

Вызов [graphics.render](../src/adapters/rendering/graphics.js#L305) занимает в среднем **21,92 мс** на старте и **27,83 мс** ночью на набережной, то есть около 96–97% измеренного игрового шага. В сцене **13 246 Object3D, 11 877 Mesh, 4 534 уникальные геометрии, 1 672 материала**, всего **308 630 экземпляров** InstancedMesh. Это инвентарь сцены, не число одновременно видимых объектов.

В 15,14-секундном CPU-профиле старта:

- `WebGLRenderer.renderBufferDirect` (`Js.renderBufferDirect` в минифицированной библиотеке): **7 138 мс inclusive**, около 47% окна.
- `Object3D.updateMatrixWorld`: **1 939 мс inclusive**, около 12,8% окна.
- `compose`: **577 мс self**; сортировка render list: **511 мс inclusive**.
- В trace зарегистрировано 657 `FireAnimationFrame`, суммарно 14 865 мс; максимум отдельного callback 26,21 мс.

Inclusive-время включает дочерние вызовы; складывать перечисленные значения как независимые затраты нельзя. Профиль показывает большой вклад обхода сцены, матриц, материалов/uniforms и отправки draw calls. Конкретный выигрыш от объединения объектов ещё не измерен.

Связанные места создания множества деталей: [geometry.detailBar / wedge](../src/adapters/rendering/geometry.js), [createTrafficCar](../src/adapters/vehicles/car-model.js), [buildQuarterLandscape](../src/adapters/world/showcase/landscape.js), [createTrafficView](../src/adapters/simulation/traffic.js). В машинах уже есть частичный batching: [createFastback](../src/adapters/vehicles/fastback.js#L24), [buildTrafficCarSuspension](../src/adapters/vehicles/traffic/suspension.js). Рабочие механизмы не следует переписывать без измеренного основания.

### 2. InstancedMesh создаётся без frustum culling — механизм и лишние отправки подтверждены

В поставляемом Three.js r149 конструктор InstancedMesh устанавливает `frustumCulled = false`. В [visual-assets.plant](../src/adapters/world/visual-assets.js#L254) каждое подробное дерево создаёт **4 200 листьев** и **240 травинок**, листья отбрасывают тени. Дополнительные группы создают [ландшафт квартала](../src/adapters/world/showcase/landscape.js), [облицовка](../src/adapters/world/showcase/cladding.js) и автомобильные сборщики. При видимых родителях такие группы проходят в рендер независимо от пересечения камерой.

Измеренные 10,5–10,7 млн отправленных треугольников почти не меняются даже в сильно различающихся ракурсах. Это согласуется с гипотезой лишней отправки экземпляров, но **не является измерением количества геометрии за камерой**.

Адресная проверка `census.js` завершилась в продолжении сессии до остановки дальнейших тестов. Получены три переписи реальных draw calls с границами экземпляров и frustum каждой камеры. Точные результаты и ограничения приведены в дополнении ниже.

Простое переключение `frustumCulled = true` в r149 опасно: границы базовой геометрии не описывают все instance transforms. Нужны корректные bounds для конкретной группы, включая запас на shader-анимацию и правильную проверку камеры теней. Отсечение только по основной камере может удалить видимые тени.

### 3. Повторный пересчёт матриц статических объектов

У всех **11 877 Mesh** в инвентаре включён `matrixAutoUpdate`; среди них много неподвижных объектов. Профиль подтверждает существенную стоимость `updateMatrixWorld` и `compose`. Нужно адресно отделить действительно неизменяемые трансформации от машин, колёс, пешеходов, лодок, камеры, солнца и других анимируемых объектов. Нельзя массово отключать обновление матриц: изменение родительского узла также влияет на потомков, а поведение `matrixWorldAutoUpdate` зависит от r149.

### 4. Долгая остановка при первом запуске

Новый браузерный контекст: navigation/load **22 310 мс**, внешнее ожидание запуска **22 511 мс**. В `startup.cpuprofile` окно 22 484 мс, создание WebGL-программ (`ys`, Three.js, строка 6, столбец 293132) занимает **18 491 мс inclusive**, из них **18 444 мс self**. Создание процедурных поверхностей `surface()` в [visual-assets.js](../src/adapters/world/visual-assets.js#L25) также заметно: крупнейший отдельный стек около **1 181 мс inclusive**. В другом уже сохранённом запуске сборка мира заняла около 3 секунд, а navigation около 21,9 секунды.

Подтверждена концентрация задержки в пути создания/проверки шейдерных программ при первом рендере. **Не установлено**, какая доля приходится отдельно на `compileShader`, `linkProgram` или синхронное ожидание `getProgramParameter`, и насколько результат зависит от состояния драйверного shader cache. Диагностический `startup-gl.js` для разделения этих API подготовлен, но ещё не выполнялся. Полностью «холодный» драйверный кеш принудительно не очищался.

Это высокий приоритет для стартового фриза, но не объяснение постоянных 34 FPS после прогрева. Прогрев шейдеров сам по себе переносит работу во времени и не доказывает уменьшения общего времени загрузки.

### 5. Тени, отражения и работа на паузе — измеренные дополнительные расходы

Проход теней занимает около **3,78–3,84 мс CPU wall time** в кадре; это часть полного рендера, не добавочное время поверх него. В [scene.js](../src/adapters/rendering/scene.js#L46) настроена карта 2048², в [lighting.updateLighting](../src/adapters/rendering/lighting.js#L81) солнце и target следуют за игроком. Простое отключение обновлений теней без учёта динамики некорректно.

[updateReflections](../src/adapters/rendering/graphics.js#L215) обновляет отражение воды примерно каждые 0,12 с у набережной, куб машины каждые 0,85 с; также есть куб квартала и PMREM. В прогретых стартовых окнах обычные кадры занимают около 22,2–23,1 мс CPU, кадры с отражением около 22,5–23,6 мс, с PMREM около 23,5–24,4 мс. Ночью соответствующие диапазоны примерно 28,1–29,1 / 28,7–29,5 / 29,4–30,1 мс. Это наблюдаемая корреляция в работающей игре, **не изолированный A/B-тест стоимости эффекта**. Подтверждения, что отражения — главная причина просадки, нет.

На паузе симуляция останавливается, но [game.step](../src/application/game.js#L36) и [runtime.frame](../src/adapters/browser/runtime.js#L12) продолжают полный рендер: 18,16 мс на `graphics.render`, 2 445 draw calls/кадр. Это лишняя нагрузка в установившейся паузе; её устранение не следует выдавать за улучшение FPS активной игры. Камера и UI могут требовать отдельных обновлений.

## Проверка памяти

Полные поэтапные значения сохранены в [performance-audit-data.json](performance-audit-data.json), раздел `memory`. Исходные записи: `artifacts/performance-audit/memory-samples.jsonl`.

Проверка использует реальную работающую игру: прогрев четырёх районов и дня/ночи; затем 10 минут поездок между районами с переключением освещения и выполнением заданий; далее 20 пауз/возобновлений, 15 повторных установок **того же high** и resize-событий, 5 перезагрузок страницы. Resize-события здесь не меняют разрешение — тестируется повторный путь настройки ресурсов. Между точками памяти вызывается сборка мусора. Кадровые массивы инструмента при длительном прогоне не накапливаются.

В проекте один постоянный игровой мир: настоящего API замены сцен или создания нового мира при «Начать» нет. Поэтому переходы между районами, смена освещения, миссии и reload — доступные проверенные жизненные циклы. Называть это тестом произвольной смены Three.js-сцен нельзя.

Различаются JS heap (`Runtime.getHeapUsage.usedSize`), backing storage, native heap браузерного движка, память процессов Chrome и счётчики GPU-ресурсов Three.js. Они не взаимозаменяемы. Working set/private memory GPU-процесса **не является прямым измерением VRAM**. В `performance.memory` может учитываться иная совокупность памяти; её нельзя напрямую сравнивать с одним JS heap.

Снимки `heap-warm-start.heapsnapshot` и `heap-after-soak.heapsnapshot` предназначены для сравнения retaining paths в Chrome DevTools. Детальный сравнительный разбор dominators отложен; одна стабильная кривая не доказывает отсутствия любых возможных утечек. Полного teardown у игрового мира нет: это потенциальный риск при будущей повторной инициализации в той же странице, а не доказанная утечка текущего сценария.

Тест завершился: длительная часть заняла **609,756 секунды**, выполнено 10 доставок, затем все 20 пауз/возобновлений, 15 повторных high/resize и 5 reload. Ошибок JavaScript в `soak-errors.json` нет.

## План оптимизации для согласования

1. **Использовать завершённую короткую проверку `census.js`** в уже выбранном стартовом ракурсе: измерить лишние отправки отдельно в основную камеру и тени. Не повторять весь первичный анализ. Зафиксировать bounds и правила их обновления для r149.
2. **Корректное отсечение групп экземпляров.** Сохранить каждый лист, травинку, деталь и исходную дальность. Использовать bounds всей группы с учётом instance transforms, родительских трансформаций и ветра. Общую геометрию нельзя наделять несовместимыми bounds разных групп. Проверить основную камеру, тени и отражения. Измерить эффект отдельно.
3. **Уменьшить draw calls статических деталей** локальным объединением/instancing совместимых непрозрачных объектов по материалам и пространственным участкам. Сохранить материалы, геометрию, UV, тени и порядок прозрачности. Начать с реально доминирующих категорий, полученных census; не переписывать все сборщики мира.
4. **Убрать доказанно лишнюю работу с матрицами** только у неподвижных объектов; проверить изменения родителей, тени и анимации. Повторно измерить долю `updateMatrixWorld` и `compose`.
5. **Отдельно устранить блокировку первого запуска:** закончить API-тайминг создания программ, определить варианты шейдеров и критический путь. Затем выбрать локальное кеширование/подготовку неизменяемых процедурных ресурсов и управляемый прогрев. Сравнивать и время до готовности, и максимальную блокировку UI, не только средний FPS после загрузки.
6. После основных улучшений повторно оценить тени, отражения, PMREM, постобработку и паузу. Менять расписание только при сохранении требуемого изображения и динамики. Мелкие расходы физики/камеры/флагов не должны отвлекать от рендера.
7. Для каждого самостоятельного изменения: одинаковые GPU, Chrome, 1920×1080, DPR1, `high`, координаты и камера, время суток, сопоставимая фаза трафика; минимум три повтора. Сравнить среднее/p95/p99/max кадра, >50/>100 мс, CPU, GPU, draw calls и retained memory. Изменение должно превышать разброс повторов; заранее обещать процент ускорения нельзя.
8. Регрессии: сравнить ракурсы и тени, сохранить состав контента и механики; проверить управление, трафик, столкновения, миссии, день/ночь, звук, паузу. Выполнить `npm run check` и функциональную браузерную проверку. Существующий browser smoke test с SwiftShader пригоден для функциональности, **не для доказательства производительности GPU**.

Цель — устойчивое приближение к бюджету 16,67 мс для 60 FPS и снижение хвостов времени кадра. Это критерий дальнейшей работы, не обещанный результат. Снижение качества, дальности, числа NPC, листвы и сложности механик в этот план не входит.

Переносимый архив `../tbs-togliatti-audit-handoff.zip` содержит весь проект и диагностические артефакты без `node_modules`. После распаковки игра запускается через `index.html`; для инструментов потребуется `npm ci` и проверка пути Chrome. На другом CPU/GPU абсолютные FPS старого компьютера нельзя использовать как контроль для доказательства ускорения: перед первой оптимизацией нужен короткий локальный baseline в тех же сценариях. Старые профили и выявленные причины повторно исследовать полностью не требуется.
