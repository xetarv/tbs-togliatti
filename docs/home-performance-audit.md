  контекст использует RTX 2080 Ti. Наличие Microsoft Basic Render Driver в списке

## Основные измерения

Результат объединяет интервалы трёх повторов: FPS = 1000 / средний интервал,
p95/p99 считаются по объединённым интервалам. Это не среднее трёх значений FPS.
Draw calls и треугольники включают все проходы кадра; GPU — асинхронные total queries.
CPU step — wall time выполнения игрового шага, включая render; это не чистое
процессорное время. CPU и GPU работают с перекрытием, их времена нельзя складывать.
GPU query измеряет elapsed time между командами, а не только активное время шейдеров;
ожидание подачи команд также может влиять на результат. Pixel/fill-rate bottleneck
и конкретный дорогой шейдер этим измерением не установлены.

### 1. Отправка множества отдельных объектов на рендер

Отдельные CPU sampling-профили поездок: 19,77 секунды для города и 16,25 для ночи.
В `assets/three.min.js`, строка 6, `Js.render` занимает 90,6% / 88,6% inclusive
времени профиля; вложенный `Js.renderBufferDirect` — **48,4% / 43,5%**, собственное
время последнего — 5,8% / 5,2%. Видны `bindVertexArray`, `uniformMatrix4fv`,
сортировка и настройка состояния. Доли inclusive перекрываются и не суммируются.
Minified-имена без точной расшифровки не получают выдуманных названий; callFrame
URL/line/column и полные CDP profiles сохранены для проверки.

Существующий census перехватывает `renderBufferDirect` на кадрах **180, 300, 450**.

### 2. Матрицы и обход scene graph

Инвентаризация текущей основной сцены: **12 049 Object3D**, **10 680 Mesh**,
1 079 InstancedMesh, 309 890 экземпляров; у **всех 10 680 Mesh включён
matrixAutoUpdate**. Это не значит, что все они статические или могут быть заморожены.
В CPU-профиле `Object3D.updateMatrixWorld` (`three.min.js:6:73576`, координаты
с единицы) занимает 8,9% / 10,6% inclusive и 7,8% / 9,4% self; отдельно виден
`multiplyMatrices` с 3,9% / 4,2% self. Инлайнинг затрудняет разделение local
composition и world multiplication: весь процент функции нельзя считать будущим выигрышем.

Frustum culling сокращает draw calls, но не освобождает от всего предшествующего
обхода/обновления матриц. Регистрация статичных узлов и кэширование локальной матрицы
могут уменьшить работу. Простое отключение world-обновлений небезопасно при движущемся
родителе; в r149 принудительное рекурсивное обновление также не устраняется одним
`matrixWorldAutoUpdate=false`. Нужны адресные изменения в местах построения.

### 3. Стоимость графических проходов

Отдельный `--probe --passes --census`, по 50 GPU-проб main/shadow/post на маршрут:

| GPU проход                             |             Город |              Ночь |
| -------------------------------------- | ----------------: | ----------------: |
| Основной render, **включая тени**      |          19,94 мс |          15,48 мс |
| Только тени                            |           2,48 мс |           2,33 мс |
| Post                                   |           0,37 мс |           0,34 мс |
| Reflection render, за измеренный вызов | 0,097 мс, 18 проб | 0,060 мс, 25 проб |

Query focus чередуется между total/render/shadow: это разные кадры одного маршрута,
не вложенные таймеры. Нельзя сложить main и shadow или вычесть их как точное время
одного и того же кадра. Reflection label включает отражательные render-вызовы;
цифра не равна стоимости всех cube faces/PMREM за кадр. Редкие обновления вне
выбранных query кадров могли не попасть в выборку. Основной рендер — явный первый
кандидат; уменьшение качества постобработки/отражений эти данные не обосновывают.

Точка кода: [createGraphics.render / updateReflections](../src/adapters/rendering/graphics.js).
Native CPU wall time `graphics.render` в стартовом виде 18,17 мс, набережной 24,62,
береге 9,71; вложенный shadow wall time 2,72 / 2,64 / 2,67 мс. Physics в неподвижных
видах около 0,04 мс, traffic simulation около 0,04, traffic view 0,07–0,12,
пешеходы 0,14–0,15. В отдельной динамической probe: `world.updateWorld` около
0,47–0,50 мс, pedestrians 0,15, camera 0,011. Это не основание упрощать механику.
Часть frozen ports harness не оборачивает, поэтому таблица systems не является
исчерпывающим разложением всего CPU step.

### 4. Размер сцены, запуск и ограничения текущих адаптеров

- Вся сцена строится заранее: измеренный `buildWorld` **3 058 мс**, navigation load
  **20 710 мс** на данном запуске. Ранее дома load был около 22,3–22,5 секунды.
  Новый холодный startup CPU/GL profile не снимался, состояние shader cache не
  контролировалось: нельзя объявлять доказанное ускорение cold start или новую
  точную причину оставшихся 20 секунд. Старый профиль компиляции шейдеров сохранён
  в первоначальном аудите. Eager build и общий scene graph ограничивают расширение мира.
- В основной сцене 4 574 уникальные геометрии, 1 672 материала, около 35,81 MiB
  geometry buffers на CPU. Это инвентаризация сцены, не объём VRAM.
- [createVegetationCulling](../src/adapters/rendering/vegetation-culling.js)
  использует r149-specific `Frustum.intersectsObject` и per-instance bounds;
  изменение instance transforms/count/атрибутов требует корректного обновления
  регистрации bounds. Новый splitter может увеличить calls; слепое уменьшение
  ячейки не гарантирует ускорения.
- Инвентаризация содержит 250 InstancedMesh с `frustumCulled=false` и всего
  3 774 экземпляра в них. **Сам по себе флаг не доказывает лишний рендер**:
  он может относиться к динамическим деталям или специально обработанным группам.
  Точный текущий процент экземпляров вне каждой camera/shadow frustum этим
  контрольным запуском не вычислялся; старый census нельзя выдавать за новый.
- [Светофорные housing batches](signal-housing-batching.md) сохраняют точные
  modelView/normal attributes и порядок по камере в
  [createTrafficView](../src/adapters/simulation/traffic.js). Связь с shader chunks
  r149 — ограничение при будущих материалах/освещении. Любое новое batching требует
  аналогичных проверок трансформаций и порядка рисования.
- [Эксперимент с общими facade materials](facade-materials.md) был отклонён и
  откачен. Он не входит в принятые оптимизации; нельзя включать его эффект в
  домашний результат или предлагать повторить без учёта найденных регрессий.

## Память: что проверено

После удаления capture-буферов и принудительного GC в каждом независимом контексте
поездки `Runtime.getHeapUsage.usedSize` составил около **45,65 MiB** в городе и
**42,80 MiB** ночью. Между тремя повторами одного маршрута различия несколько KiB.
Backing storage отдельно: 66,00 / 65,98 MiB. Не смешивать эти показатели с
`performance.memory.usedJSHeapSize`, который учитывает данные иначе.

Ресурсы после города во всех трёх повторах: **3 219 geometries, 233 textures,
86 programs**; после ночи: **2 335, 183, 74**. DOM: 2 documents, 771 / 775 nodes,
70 listeners, без роста между независимыми повторами.

В одном native-контексте после последовательного посещения видов JS heap в конце
окон был 46,7–70,6 MiB без принудительного GC; renderer resources достигали
3 434 geometries / 238 textures / 87 programs. Начальные значения ниже из-за
ленивого создания GPU-ресурсов при встрече объектов. Сырые изменения сохранены.

Эти данные **не доказывают отсутствие утечек при часовой игре или повторных стартах
в одном контексте**: отдельного длительного soak/restart теста здесь не было.
Индивидуальный объём VRAM игры и resident memory процесса не измерены.
Нельзя называть число geometries/textures байтами VRAM или объявлять их рост утечкой
без анализа lifetime и plateau. Для будущего memory A/B требуется сравнивать
одинаковый маршрут и число циклов после GC.

## Три следующие оптимизации

Это предложения, а не измеренные ускорения. Порядок учитывает ожидаемую пользу,
объём работы и риск; конкретный прирост FPS не обещается.

| Приоритет | Изменение                                                                  | Ожидаемая польза                                                                                                   | Сложность                              | Риск изображения                                                      |
| --------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------- | --------------------------------------------------------------------- |
| 1         | Адресное пространственное batching оставшихся статических деталей          | Снижение calls и числа обходящихся Mesh в нескольких проходах; подтверждённые повторяющиеся trim/lane/grass детали | Средняя                                | Средний: порядок, точность transforms, culling/shadow bounds          |
| 2         | Кэширование локальных матриц явно статичных узлов                          | Снижение части подтверждённых затрат updateMatrixWorld; draws/GPU автоматически не уменьшаются                     | Низкая–средняя                         | Низкий при точном списке статичных узлов; высокий при массовом freeze |
| 3         | Повторное использование геометрий и выборочное batching деталей транспорта | Крупный потенциальный draw-call резерв: около 905 main + 444 shadow calls в выбранных городских кадрах             | Низкая для reuse; высокая для batching | Низкий для reuse, средний–высокий для batching движущихся деталей     |

**1. Статические детали — рекомендуемый следующий отдельный эксперимент.**
Файлы/functions: `population.js:populateWorld`, `buildings/components/trim.js:buildBuildingTrim`,
`roads.js:createRoads`, `terrain.js:createTerrain`, существующий bounds adapter.
Начать с одной подтверждённой категории `trimMat:BoxGeometry`: найти её обычные
статические Mesh, сохранив все экземпляры, материал, флаги теней, transform и
пространственные ячейки. Затем отдельно lane/grass, если первая категория прошла gates.
Не объединять разные facade materials и не менять принятую растительность.
Проверить UV, normals, cast/receiveShadow, границы main/shadow/reflection cameras,
прозрачность и порядок равных глубин. Новый InstancedMesh может изменить floating-point
путь, поэтому простая замена Mesh на instance не считается визуально безопасной заранее.

Проверка: полный state/camera trace, PNG на кадрах 180/300/450 и terminal framebuffer
для обоих маршрутов; статические старт/ночь/берег, вращение камеры и границы ячеек;
существующие тесты. Измерение: изолированный A/B на этом ПК, чередование before/after,
не менее трёх прогретых повторов, те же routes/viewport/High, calls по проходам,
CPU/renderBufferDirect, GPU total, p95/p99, retained resources. Если появляется
визуальная регрессия, уменьшить scope или отклонить изменение. Считать выигрыш
только по A/B, а не по теоретически удалённому числу Mesh.

**2. Локальные матрицы.** В местах построения `populateWorld`, `buildBuildingTrim`
и статичных signal heads в `createTrafficView`: один `updateMatrix()` после
окончательного position/quaternion/scale, затем `matrixAutoUpdate=false` только
на проверенных неизменяемых объектах. Сохранить обычные world updates, динамические
car/wheel/pedestrian parents, камеру, ветер и лампы. Риск — поздний builder или
анимация меняет transform; массовый обход с отключением всех матриц запрещён.
Проверка — те же trace/pixel gates, смена времени суток и движение родителей.
Измерение — CPU sampling и wall render A/B, p95/p99; число draws и GPU должно
контролироваться независимо. Даже полный успех этой меры не гарантирует 60 FPS
при нынешних 21 мс GPU в городской поездке.

**3. Транспорт.** `traffic/wheels.js:buildTrafficCarWheels` создаёт одинаковые
CylinderGeometry/TorusGeometry для каждого колеса; `car-model.js:createTrafficCar`
и `animateVehicle`, `traffic/suspension.js:buildTrafficCarSuspension` связывают
движущиеся родители. Сначала отдельный узкий reuse идентичных геометрий, как
рекомендовано последним сохранённым отчётом: сохранить Mesh, материалы, сортировку,
обычные матрицы и владельцев dispose. Это уменьшает allocations/VAO switches,
**само по себе не сокращает draw calls**. Затем отдельный эксперимент с объединением
спиц/непрозрачных деталей внутри одинаково анимируемого родителя, без изменения
физики/колёс/числа машин. Пропуск geometry constructors может изменить потребление
Math.random для UUID и процедурное поколение; seed/trace должны остаться совпадающими.
Проверить normals, steering/rolling/suspension, shadow passes и sort/precision.
Измерение — targeted wheel/body census, retained geometry и startup build time,
затем те же динамические A/B и visual gates. Transport batching имеет большой
потенциал, но больший риск и трудоёмкость, поэтому не смешивается с первым изменением.

Кэш теней, изменение отражений, streaming мира и предкомпиляция шейдеров могут
потребоваться при расширении игры, но этот аудит не измерил безопасный выигрыш
таких решений. Особенно shadow caching требует раздельных static/dynamic casters
и корректной инвалидации при смене света/камеры. Снижение разрешения эффектов,
плотности мира, дальности и качества здесь не рекомендуется.

  все шесть первичных поездок, telemetry, pixel/trace hashes, heap/DOM после GC.

  соседние probe JSON/frames/traces/PNG сохранены отдельно от primary.

  `adaptation.json`, `analyze.cjs`, `inspect-summary.cjs`, `verify.cjs` и журналы:
  точная методика и возможность повторной обработки без запуска браузера.

Для **повторной обработки существующих данных**, без новых измерений:

```powershell
node artifacts/home-performance-audit/analyze.cjs
node artifacts/home-performance-audit/inspect-summary.cjs
```

Для будущего согласованного контрольного прогона, из корня проекта, последовательно:

```powershell
node artifacts/home-performance-audit/native.cjs baseline
$env:TBS_BROWSER = 'C:\Program Files\Google\Chrome\Application\chrome.exe'

```

Не запускать эти команды поверх сохранённого baseline: сначала скопировать весь
каталог результатов вне выходного каталога и дать следующему запуску новые пути.
