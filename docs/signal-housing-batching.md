# Объединение неизменных деталей светофоров — этап 4

## Решение

Оставлена одна оптимизация: 1260 неподвижных стоек, корпусов и козырьков 252 светофорных heads объединены в 40 InstancedMesh по исходному материалу и участку 84 × 80. Все 756 ламп остаются отдельными исходными Mesh. Переключение фаз, транспорт, физика, UI, освещение, настройки и предшествующие оптимизации не изменены. Three.js остаётся r149.

Прирост небольшой, но повторяемый в проверенных условиях: +3,27% FPS в городе и +3,48% у набережной. Во всех трёх повторах FPS новой версии выше максимума трёх контрольных повторов соответствующего маршрута. Качество изображения подтверждено на перечисленных ниже кадрах, а не для всех возможных положений камеры.

## Причина прежних различий и контроль стабильности

Повторно сравнены сохранённые PNG предыдущего эксперимента, с декодированием RGBA:

| Вариант / сравнение                                              | Город, различающихся пикселей |     Набережная ночью |
| ---------------------------------------------------------------- | ----------------------------: | -------------------: |
| Исходник, повтор 1 / повтор 2                                    |                             0 |                    0 |
| Прежний instancing, повтор 1 / повтор 2                          |                             0 |                    0 |
| Прежний instancing / исходник                                    |        131, максимум ΔRGB 110 | 49, максимум ΔRGB 33 |
| Исходная проекция вершин, обычные instanced-нормали              |                             0 |  1, максимум ΔRGB 33 |
| Исходная проекция и матрицы нормалей, без сортировки экземпляров |                             0 |  1, максимум ΔRGB 33 |
| Исходная проекция, матрицы нормалей и порядок деталей            |                             0 |                    0 |

Основная причина — другой численный путь преобразования вершин. Обычный Mesh получает `modelViewMatrix`, вычисленную на CPU из исходных double-матриц и преобразованную в Float32 при загрузке uniform. Обычный instancing сначала умножает вершину на Float32 `instanceMatrix`, затем на матрицу камеры на GPU. Математически одинаковое выражение округляется иначе. На маленьких дальних лампах это меняет покрытие пикселей и результат проверки глубины. Исправление только проекции убрало все дневные различия и 48 из 49 ночных.

Оставшийся ночной пиксель (120,239: RGB 0/0/0 → 0/21/33) исчез только после восстановления сортировки деталей по глубине и исходному `Object3D.id`. Это подтверждает влияние порядка рисования перекрывающихся корпуса и козырьков, вероятно при равной квантованной глубине. Сам depth buffer отдельно не считывался: равенство его значений остаётся объяснением, а не прямым измерением. Нормали отдельно этот пиксель не устраняли. Повторные исходные снимки были стабильны; шум теста не объясняет различия.

Исходные материалы `dark` и `trimMat` сохранены как те же объекты. Корпуса исходно имеют `castShadow=false`, `receiveShadow=false`; поэтому изменение теневого прохода не объясняет прежний дефект.

## Реализация и ограничения r149

- Для каждого экземпляра сохраняются исходные double-матрицы. Для каждой основной камеры вычисляются точно те же CPU `modelViewMatrix` и inverse-transpose `normalMatrix`, что для обычного Mesh; в GPU-атрибуты записывается Float32. Unit-тесты сравнивают эти значения без допуска, включая преобразованный родитель и смену камеры.
- Специальный vertex shader заменяет только преобразование позиции и нормали. PBR fragment shader, цвета, roughness, metalness, карты, tone mapping и освещение сохранены. Используются 14 vertex attribute slots при аппаратном лимите 16; программы прошли проверку Edge.
- Для batch используется исходный material, включая его `id` и порядок opaque-сортировки. Шейдерные callbacks временно устанавливаются в `onBeforeRender` batch и восстанавливаются в `onAfterRender`. Отдельный постоянный ключ программы предотвращает смешивание с обычными Mesh/InstancedMesh того же материала. Проверено восстановление callbacks и отсутствие изменений остальных изображений. Число shader programs выросло ровно на один, без роста по повторам.
- Атрибуты подготовлены через существующий `scene.onBeforeRender`, с сохранением предшествующего callback. В r149 загрузка geometry attributes выполняется при обходе сцены; подготовка в `object.onBeforeRender` давала задержку на кадр и была отклонена экспериментально.
- Экземпляры внутри каждой группы сортируются по тому же projected depth и исходному object id, что исходные opaque Mesh. Переставляются согласованно и `instanceMatrix`, и camera/normal attributes.
- Используется уже проверенный адаптер границ r149, без изменения его кода. После изменения порядка обновляется версия instance buffer и группа повторно регистрируется. Это не оставляет её в состоянии fail-open из-за изменённого буфера. Bounds учитывают все экземпляры и родительскую матрицу; тест проверяет сохранение видимых деталей после перестановки.
- Флаги теней сохранены. Эти детали не являются ни casters, ни receivers. Лампы и остальные casters не изменены. Существующая отражательная proxy-сцена не содержит исходных heads и не получает новые batches; её состав сохранён. В проверенных кадрах тени и отражения совпали вместе со всем framebuffer.
- `?signalHousingBatching=0` сохраняет исходные отдельные детали внутри heads, а не только отключает culling. Для основных A/B использован неизменный snapshot с обеими предыдущими успешными оптимизациями, не чистый Git HEAD aa61f93.

## Измерения

Разрешённый Edge, отдельный headless-профиль, аппаратный ANGLE NVIDIA RTX 3050 Laptop / D3D11. 1024 × 768, DPR 1, High. Сохранён существующий запуск `file://index.html`. Порядок ABBAAB, по три повтора каждой версии на каждом маршруте, 120 кадров прогрева и 600 кадров работающей игры. Штатный `game.step(1/60)`, автомобиль, трафик, пешеходы, вращение камеры и эффекты работают. Полный аудит не повторялся.

Рост треугольников объясняется консервативными групповыми bounds вместо индивидуального culling каждой коробки. Плотность, дальность и содержимое не сокращены. Дополнительный retained heap около 1,26 МиБ (1,1–1,2%). GPU byte usage API не предоставляет: фактически измерены числа geometry/texture ресурсов, не их байты. Средняя наблюдавшаяся частота: город 851,9 → 808,4 МГц, ночь 949,1 → 945,3 МГц. Рост FPS не сопровождался повышением средней частоты GPU. Полная telemetry сохранена; прогоны из предыдущего этапа и промежуточных экспериментов не смешаны с этой таблицей. npm check и другие браузерные тесты одновременно с основными измерениями не запускались.

## Изображение, игровой процесс и тесты

- Все 12 конечных framebuffer основного A/B совпали с соответствующим контролем, включая повторные контрольные снимки.
- Отдельный visual A/B сравнил 8 пар RGBA-изображений: кадры 180, 300, 450, 600 каждого маршрута. Во всех парах 0 различающихся пикселей. Его FPS исключён из таблицы: захват PNG добавляет накладные расходы.
- Хеши всех 600 состояний каждого маршрута совпали: player, camera, 36 транспортных средств, 59 пешеходов, mode и mission counters. Автомобиль проехал 73,97 / 78,48 единицы, повернул на диапазон heading 1,56 / 1,58 рад. Это не замороженный рендер.
- `npm run check`: ESLint, Prettier, 45 тестов прошли. Четыре новых теста проверяют состав/матрицы/материалы/теневые флаги, неизменность всех фаз ламп, точные Float32 camera/normal matrices и восстановление callbacks, сортировку и корректность bounds после перестановки.
- Edge: ошибок загрузки, JS и компиляции шейдеров нет. Порядок script tags и зависимости не изменены.

## Оставшиеся риски

Сопоставление подтверждено на RTX 3050 Laptop в перечисленных динамических сценах. Другие GPU/драйверы, все возможные ракурсы, native variable-dt scheduler и длительный прогрев не измерены. При совпадающих depth значениях с посторонней геометрией batching потенциально может изменить порядок между группами; проверенные кадры этого дефекта не показали. Сортировка внутри группы сохраняет исходный порядок деталей.

Путь рассчитан на текущие неподвижные heads, положительные масштабы деталей, непрозрачные StandardMaterial без tangent/transmission и обычную PerspectiveCamera. Движение Scene-родителя и смена камеры проверены тестами; будущая анимация отдельных heads, новые материалы, XR/ArrayCamera или включение теней у этих деталей потребуют повторной проверки реализации. CPU-подготовка матриц, сортировка и обновление bounds имеют цену, поэтому сокращение draw calls существенно больше прироста FPS. Дополнительные CPU/GPU оптимизации в этом проходе не выполнялись.
