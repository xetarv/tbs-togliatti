# Работа с TBS Togliatti 2040

## Начало и навигация

- Перед изменениями проверь рабочую папку, ветку, HEAD, remote и `git status`.
  Сохраняй существующую работу; не предполагай, что локальные коммиты опубликованы.
- После этих правил найди заголовок нужного раздела [карты архитектуры](docs/refactoring.md)
  через `rg -n '^#{1,3} '`, прочитай раздел, затем целевой модуль, его контракт в `types/`
  и непосредственного потребителя. Расширяй чтение только для конкретного открытого вопроса.
- Для восстановления контекста достаточно верхней актуальной записи
  [состояния проекта](docs/project-state.md). Журналы миграции, аудиты и `artifacts/`
  открывай только по конкретной задаче; не перечитывай их целиком.
- Ищи через `rg` / `rg --files` в выбранных путях. Уже прочитанные правила, контракты и
  установленные связи используй повторно в текущей сессии; перечитывай при их изменении
  или пробеле контекста. Фабрики зарегистрированы в `TBS`, а не в runtime exports.
- Ограничивай вывод диапазоном строк/совпадениями; при усечении читай недостающий фрагмент,
  а не весь файл заново. Успешные команды — краткий итог; полный лог нужен для разбора сбоя.

## Границы и совместимость

- `domain` — правила и данные без браузера/Three.js; `application` — сценарии через
  переданные порты. Они используют только собственный `globalThis.TBS.domain` либо
  `.application`; ESLint запрещает зависимости от внешних адаптеров.
- `adapters` реализуют браузер, ввод, UI, звук и 3D. `bootstrap` передаёт зависимости.
  Различай `GameState`, `PresentationState` и `WorldConstructionState`.
- Сохраняй Three.js r149, `file://index.html`, classic scripts и порядок в `index.html`.
  Используй существующий `window.TBS`; не вводи runtime ESM, bundler или HTTP-сервер.
- Редактируй TS-исходники, не `dist`. Сгенерированные JS хранятся вместе с исходниками.
  Новый модуль требует проверки регистрации, контракта и позиции скрипта.
- Сборка/strict typecheck используют TS7 (`@typescript/native`); TS6 — только API ESLint.
  Не ослабляй strict, ESLint, охват исходников и деклараций. Не скрывай несовместимости
  через `any`, подавления или необоснованные `as`/`!`.
- Сохраняй графику, физику, batching/instancing/culling и диагностику, если задача
  прямо не разрешает их изменение. Ограничения расширения перечислены в карте.

## Проверки, Git и завершение

- Только документация: проверь пути/имена, форматирование изменённых документов и
  `git diff --check`; build/check и браузер не нужны.
- Код/контракты: сначала необходимые адресные проверки, затем один финальный
  `npm run build && npm run check`. `check` уже включает тесты: не дублируй npm test
  или typecheck. В PowerShell при блокировке npm.ps1 используй npm.cmd.
- Браузер проверяй адресно при изменении DOM, WebGL, порядка загрузки или запуска.
  Существующий способ — `tools/check-browser.cjs`; он пишет снимки в `artifacts/`:
  сохраняй прежние результаты и используй отдельное место для новых.
- Повторяй проверки только после влияющих изменений или для разбора конкретного сбоя.
  AST не доказывает пиксельное совпадение; FPS требует отдельного измерения.
- При конфликте истории, посторонних изменениях, риске потери данных или необходимости
  выйти за разрешённый объём остановись и объясни препятствие. Не меняй ACL и ограничения ОС.
- Не выполняй commit/push без разрешения. Если коммит разрешён: проверь локальное
  авторство `xetarv <335514432+xetarv@users.noreply.github.com>`, добавляй точные пути,
  проверь staged-список и `git diff --cached --check`. Глобальную Git-конфигурацию не меняй.
- Не применяй `reset --hard`, `clean`, rebase, force push или переписывание коммитов
  без отдельного явного разрешения. Не удаляй пользовательские файлы и диагностику.
- Короткий отчёт: изменение и причина, проверки/ограничения, Git status и SHA коммита.
  Не повторяй историю задания и успешные логи. Шаблон задания — в карте; следующие этапы не начинай.
